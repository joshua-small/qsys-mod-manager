# Repository-owned catalog publishing

Each approved mod repository owns `catalog/mod.json`, `catalog/icon.ico` (or another local PNG/JPEG/ICO), and `catalog/releases/<tag>.md`. Descriptions and release notes are copied verbatim; there is no README scraping or generated summary. The existing generic icon is starter artwork owned separately in each repository.

The manager's `catalog/index.json`, `catalog/presentation.json` and `catalog/sources.json` are generated output. Do not edit their content by hand. The first two retain schema 1 so older manager readers still work. The manager embeds these generated documents for offline descriptions and presentation. The compiled ID/repository/module/shared-file allowlist and canonical package name remain approval rules, not an editable content catalog.

## Release path

1. Update the mod's content, artwork and plain-text notes before tagging. Use a GitHub username for author. Help links must remain in the approved mod repository; artwork paths must stay under `catalog/`.
2. Publish a stable GitHub release with exactly one existing `.qdsmod` package. The mod workflow calls manager tooling pinned to an immutable commit.
3. The publisher validates identity, tag/assembly version, exact Designer 10.5 host/common hashes, package structure, allowed module/marker files, shared dependency hashes, payload hashes/sizes and assembly identity using `ModPackage.Open`. No mod code is executed. It downloads source metadata and artwork at the checked-out commit to verify provenance.
4. It attaches `qmm-catalog.json` without replacing an existing asset. That bounded record contains the package URL/hash/size, compatibility, content commit, copied text/notes, and image hash. A repeat is idempotent; changed content for the same release is rejected.
5. The manager checks hourly, or through **Catalog → Run workflow** on main. It reads only repositories in the approved allowlist, skips drafts/prereleases and releases without a completed record, follows bounded trusted-host downloads, re-verifies source content and the full package, and generates all three catalog files together.
6. A bot opens or updates `codex/generated-mod-catalog` for human review. It never commits catalog changes directly to main, approves its own PR, or merges it. Approve any held CI run, review the changes, then merge through the normal process. Only then do users see the new catalog.

The manager repository must allow GitHub Actions to create pull requests (Settings → Actions → General). The workflow requests only contents/PR write access for the proposal job. If repository policy blocks PR creation, the job reports failure, retains the proposal branch and uploads the generated files; a maintainer can open the branch's PR manually. No cross-repository credential, repository dispatch secret or new service is needed. Published mod records are collected with read access.

GitHub schedules may be delayed; use manual collection when immediate review is needed. A GitHub release generated by another workflow using its default token may not trigger a subsequent release workflow: that producer must explicitly call the reusable publisher or dispatch **Mod catalog** after attaching the package.

## Ownership and history

`mod.json` schema 1 fields are `schema`, `id`, `name`, `description`, `author`, `thumbnail` (relative path), and `helpUrl`. Names remain the canonical approved package names; renaming or supporting another mod requires a manager approval change. Descriptions are bounded to 4,000 characters, notes to 12,000, image files to 1 MiB, and record files to 64 KiB. Thumbnails use commit-pinned raw GitHub URLs. The native client retains bounded decoding, cache and fallback behavior.

An approved release's package URL, size, hashes and compatibility are immutable. Its source receipt also prevents silent replacement of notes, artwork or the content commit. Append a new release for changes. The newest version supplies current mod presentation; a late historical record cannot roll it back. Historical entries, notes and release assets remain available for exact-version profiles. Missing or changed approved records fail collection without publishing anything. Data-only content cannot expand installation support, change approved files, or bypass the user's preview/apply step.

The protocol is intentionally bounded by the current supported catalog (100 releases per mod and 256 KiB per client document). Reaching a limit produces an explicit error, not silent truncation. New mods still require a reviewed manager release.

## Migrating existing releases

The original v0.15.0 Schematic Tools and v0.1.1 Automatic Geometry tags predate owned metadata. After merging their content PRs, run their **Mod catalog** workflow on main with the original tag and **Content ref** set to the merged content commit. This records the exception explicitly in provenance; no tag, package or original release body is rewritten. Future releases leave Content ref blank and use their release tag.

Merge the manager tooling first, then the two mod PRs whose workflows pin that tooling commit. Publish the two historical records, run manager collection, and approve its generated catalog PR. Existing generated text remains as the migration baseline until those records are published and reviewed. Do not publish records from unmerged feature branches merely to make a development check pass.

## Validation

`dotnet run --project CatalogTests/QdsModManager.CatalogTests.csproj -- <verified-package-directory> <new-fixture-directory>` exercises real supported packages, source ownership, tampering, compatibility, immutable history, idempotence, offline failures and trusted download bounds.

The Catalog workflow validates generated output against published records. The Windows installer workflow continues to validate native builds, grouped transactions, offline packages, recovery and installer compatibility. This content pipeline makes no new Designer or hardware acceptance claim.
