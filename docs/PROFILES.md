# Profiles and grouped operations

Profiles are metadata-only JSON (`.qdsprofile`), schema 1. Each has a stable UUID, display name, Designer version and exact host/common hashes, and a unique set of supported mod IDs with exact assembly versions, package SHA-256 hashes and enabled states. Import validates bounded metadata and creates a new identity without applying it. Packages remain separate `.qdsmod` files.

The profile library lives beside existing settings in `%LOCALAPPDATA%\QDS Mod Manager\profiles.json`. Opening a supported installation captures its existing managed configuration as an initial profile; this does not modify installation files or erase old packages/backups. Unknown files are never included in a profile. A saved profile can be assigned to several installations. Each installation retains its own applied snapshot until explicitly changed. An assigned profile cannot be deleted; switch its installations first.

Library schema 2 distinguishes an installation's applied configuration from the preview's file stamp. Adding approved mods or layouts must not make an unchanged installation overwrite another installation's newer saved profile pins. Schema-1 libraries migrate using their original file order; profile exports remain schema 1.

Registry schema 2 adds the applied profile snapshot and suspension flag to the existing managed mod records. Older schema-1 state remains readable. The next successful operation upgrades it. A previous manager cannot manage schema-2 state; use the new manager's Undo rather than downgrading the application to change mods.

Profile switching, bulk installs/updates and suspension use one journal and one installation lock. Preparation resolves every exact pin from the trusted catalog, verified imported packages or the installation's verified package store. All downloads finish before the optional preview and any installation write. Missing or incompatible pins reject preparation. Apply checks the prepared stamp and rebuilds/verifies the entire change. Package/profile build declarations still identify the tested package set; they do not certify an untested installation. The worker verifies the prepared Designer hashes and rejects a changed build. Shared-file, reparse-path, external-edit and running-Designer checks remain in effect. File and state changes share the same verified before/after backups. Rollback, interrupted recovery and Undo restore the complete applied snapshot, including suspension. Shared libraries and unrecognized modules are retained.

The per-user `previewChanges` preference defaults to false, including when absent from older settings. Turning it on restores the review dialog for changes. Dependencies, untested-version acceptance and close-Designer prompts are independent of this preference.

Untested builds require an acknowledged operation plan. After explicit warning acceptance, schema-2 installation state may carry `untestedRuntime: { schema: 1, target, hostSha256, commonSha256 }` when Mods Core is enabled and managed mods are not suspended. The target is the normalized absolute installation path; hashes identify the actual host files. A matching saved opt-in avoids repeated warnings when previews are off. A build/path change requires new acceptance. Suspending, disabling or removing Core clears consent; tested builds omit it. Undo and recovery restore the exact prior state, including any prior consent, instead of creating fresh consent. This field is never part of a portable profile. Older Core releases do not consume it. New Core startup reads it only for untested hosts and fails closed for missing, mismatched, linked or malformed state. These checks permit startup; they do not prove runtime compatibility.

Suspension removes only the private files in each managed package while retaining desired enabled states in the profile. Modern packages have no enable markers; historical schema-1 packages retain their required marker as part of exact restoration. Resume restores only enabled pins. Individual mod changes are unavailable during suspension; bulk updates can revise pins while leaving managed mods suspended. Successful individual changes revise the applied profile. The UI reconciles committed installation state into the library, including after an interrupted UI handoff or undo. Other installations are never written by this reconciliation.

Starting with 0.7.0, the manager reads approved definitions, the index and presentation together from the separate catalog's signed feed; see [catalog publishing](CATALOG-PUBLISHING.md). The old schema-1 endpoint remains frozen for older managers. Author values are GitHub usernames; artwork is optional, bounded and hash-verified. Failed artwork loading falls back to the app icon. The generator appends releases and rejects changed pins; retain historical package assets so exact profiles remain resolvable. Older locally supplied packages remain resolvable through verified cache/import even when never published.

New transaction journals use schema 2 and retain a checksum of their complete approved file-name set. Historical schema-1 journals retain their original fixed file set and ordering. Catalog growth does not invalidate either form of undo or recovery; truncated journals are rejected. Continue using 0.7.0 or newer after making these changes rather than downgrading the manager.

Source acceptance is distinct from Designer acceptance. Tests exercise file operations on disposable fixtures; no DSP/Core behavior or Designer acceptance of new extensions is claimed.
